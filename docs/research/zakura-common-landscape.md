# Zakura Common landscape for zcash.js

Research date: **2026-09-04**. The original research and this documentation revision use the source snapshots identified below; this is not an end-of-day snapshot. Scope: research and API planning only. **Architecture and proposed API names below are PRELIMINARY, not an approved public API.**

## Owner scope and integration direction

The [decision log](../planning/decision-log.md) records the 2026-09-04 owner decisions and governs product scope. **Transparent + Sapling + Ironwood** is primary; Sprout is deferred and backtrackable. The broader crate inventory below remains source evidence, not a product support commitment. Ironwood is not interchangeable with Orchard: exact Common/wallet API coverage, transaction/PCZT/proving flows, circuit versions and network applicability require validation. No activation fact is asserted here.

Forking Zakura and adding a WASM binding layer is acceptable. Prefer a new wrapper crate/workspace member depending on Zakura crates, with preliminary wrapper features such as `transparent`, `sapling`, `ironwood` and `proving`. A feature flag alone does not create JS exports or ownership/type-conversion contracts. Avoid changes to existing Zakura packages unless target compilation requires a minimal upstreamable dependency feature or fix.

The npm product starts WASM-first in Node and browser behind one TS API. Refined [D07](../planning/decision-log.md) and the [host architecture](../planning/wasm-host-architecture.md) supersede earlier native-Node/host-storage alternatives: bundled SQLite inside WASM, Node filesystem VFS and browser OPFS VFS, separate baseline/shared artifacts. Native/N-API acceleration and performance comparisons are deferred to the [future benchmark issue](../planning/future-issues.md#issue-11-wasm-performance-and-possible-native-acceleration).

D07 selects Rust-owned SQLite with a browser worker/custom OPFS VFS; D08 selects independent public/light/wallet clients and host transports without project-operated infrastructure. Runtime durability and transport interoperability still require validation. External signer/PCZT seams are first-class now. The owner's report of Ledger/external signer support in the Vizor ecosystem is useful architectural context, not validated Ironwood/device coverage. Remote proving is separately deferred; a capability-oriented prover interface should allow future explicitly authorized remote jobs without assuming local memory handles or silently disclosing witnesses.

## Findings and evidence rules

Zakura Common already exists as public Rust code and published packages. It is **not one prospective crate named `zakura-commons`**. Its primary repository is [zakura-core/common](https://github.com/zakura-core/common/blob/2e501116b60741136db21f4584f0d6d8378444a6/Cargo.toml), a 17-member crypto/protocol workspace. A separate [zakura-core/wallet-libraries](https://github.com/zakura-core/wallet-libraries/blob/a9142ee100b3a563b7d9ba7a8e94201d00ad8154/Cargo.toml) workspace contains four wallet-layer packages. “zakura-core” is the GitHub organization in these URLs; a repository literally named `zakura-core/zakura-core` could not be established from the material retrieved.

The [29 August announcement](https://zakura.com/announcements/zakura-common/) calls the launch “Zakura Common 1.0,” describes crypto optimizations and adoption by Zakura/Tachyon, and says wallet libraries will eventually include PIR work. These are first-party statements, not independently reproduced performance or security results. The [registry records](https://github.com/rust-lang/crates.io-index/blob/master/za/ku/zakura-orchard) now include Common **1.1.0**. The [wallet source pin](https://github.com/zakura-core/wallet-libraries/blob/a9142ee100b3a563b7d9ba7a8e94201d00ad8154/manifests/sources.toml) still selects **1.0.0**, so “use latest Common plus latest wallet crates” is not a validated dependency plan.

Evidence labels used throughout:

- **Source-observed:** an API, feature, or limitation present in the inspected source snapshot. Not necessarily identical to a published archive.
- **Registry-observed:** a package/version/checksum exists in the crates.io index. Not a claim that its docs build, browser build, or runtime works.
- **Announced:** a maintainer statement or future plan. No missing API is inferred.
- **Proposed / unverified:** a zcash.js design hypothesis or validation task.

The [launch announcement](https://zakura.com/announcements/zakura-common/) reports hardware-specific improvements of over 14× for mobile proving, over 5× for desktop proving, over 21× for Sinsemilla hashing, over 1.5× for trial decryption and 4–8× for proof verification. These are announced measurements, not zcash.js/browser benchmarks; no such speedup is assumed in this design.

No production source, dependencies, builds, cryptographic tests, browser benchmarks, or prototypes were added or executed. This is an architectural inventory, not an exhaustive rustdoc symbol listing or a cryptographic audit.

### Security and maturity qualifications

The [Orchard changelog](https://github.com/zakura-core/common/blob/2e501116b60741136db21f4584f0d6d8378444a6/crates/orchard/CHANGELOG.md) gives concrete fork-specific API evidence: proving/verifying-key preparation, batched Merkle combination and reusable Merkle workspaces. It dates 1.1.0 to 2026-09-04 and documents that prepared proving can operate under the default multicore configuration without requiring orbit MSMs; the 1.0.0 notes describe different feature-dependent behavior. This makes exact versions/features material to host initialization and memory policy. The changelog dates 1.0.0 to August 28, while the launch announcement and registry-facing documentation identify August 29; changelog dates are not necessarily publication timestamps.

Published 1.x packages and the node's adoption are evidence of real integration, not evidence of independent review or browser suitability. The inspected [Pasta crate](https://github.com/zakura-core/common/blob/2e501116b60741136db21f4584f0d6d8378444a6/crates/pasta_curves/src/lib.rs) explicitly disclaims constant-time field/curve arithmetic. [Halo 2](https://github.com/zakura-core/common/blob/2e501116b60741136db21f4584f0d6d8378444a6/crates/halo2_proofs/src/lib.rs) says proving and multiexponentiation are not constant-time with respect to witnesses/blinding/scalars. [BLS12-381 module documentation](https://github.com/zakura-core/common/blob/2e501116b60741136db21f4584f0d6d8378444a6/crates/bls12_381/src/lib.rs) contains an unaudited-implementation warning. These statements require a concrete threat-model decision before adopting the stack for secret-dependent operations; Rust/WASM and worker isolation do not establish constant-time behavior.

The inspected source includes protocol-version and Ironwood-related work in [Orchard](https://github.com/zakura-core/common/blob/2e501116b60741136db21f4584f0d6d8378444a6/crates/orchard/src/lib.rs) and [transaction builders](https://github.com/zakura-core/common/blob/2e501116b60741136db21f4584f0d6d8378444a6/crates/zcash_primitives/src/transaction/builder.rs). Neither code presence, an unstable feature, nor a benchmark is proof of consensus activation. Activation heights and branch/version compatibility need their own pinned protocol review before implementation.

### Lessons to reuse and gaps to validate

Reuse the workflow decomposition: small key/request packages, typed Rust bindings, separate PCZT signer authority, viewing-key wallet imports, explicit birthdays/confirmation policy, and a real browser/Snap consumer to expose integration friction. Compare these against zcash.js's **PRELIMINARY** package boundaries before choosing new abstractions. Do not claim separated signing or modular packaging as differentiation by themselves.

Potential differentiation is **PRELIMINARY and unvalidated**: a complete query and wallet API with explicit transport/storage/prover capabilities, stable error and serialization contracts, lazy proving assets, bounded jobs and documented runtime fallback behavior. Validate each claim against WebZjs exports and artifacts; a missing method in this pinned binding inventory does not establish that no downstream implementation exists.

Prior-art review targets include snapshot design and reorg recovery (without a portability promise); PCZT bytes versus serde JS objects; numeric/txid representations; multi-account signing and Sapling proof-generation authority; parameter/key memory and cancellation; and startup/worker/secret lifetimes. The PCZT wrapper uses `unwrap` on malformed input, the prover assumes non-dummy Sapling spends belong to one account, and birthday detection starts at a hard-coded height of 419200. Those are concrete review targets, not demonstrated exploits or proof that supported workflows fail. The binding comment claiming a Sapling proof-generation key can come from a UFVK should not be copied: the keys binding exposes that conversion on the USK. [PCZT parsing](https://github.com/ChainSafe/WebZjs/blob/a50df944c32243cb8da9f86e7d52cb65ac926439/crates/webzjs-common/src/pczt.rs), [prover](https://github.com/ChainSafe/WebZjs/blob/a50df944c32243cb8da9f86e7d52cb65ac926439/crates/webzjs-wallet/src/wallet.rs), [wallet bindings](https://github.com/ChainSafe/WebZjs/blob/a50df944c32243cb8da9f86e7d52cb65ac926439/crates/webzjs-wallet/src/bindgen/wallet.rs), [key conversion](https://github.com/ChainSafe/WebZjs/blob/a50df944c32243cb8da9f86e7d52cb65ac926439/crates/webzjs-keys/src/keys.rs).

Proposed dependency rule: resolve **one coherent crypto type family** within a Rust artifact. Ordinary upstream wallet crates can pull upstream Orchard/primitives alongside Zakura equivalents; identical-looking Rust types from different packages are not interchangeable. The wallet repository includes [graph checks](https://github.com/zakura-core/wallet-libraries/blob/a9142ee100b3a563b7d9ba7a8e94201d00ad8154/scripts/verify-zakura-graph.sh) and [explicit rewiring](https://github.com/zakura-core/wallet-libraries/blob/a9142ee100b3a563b7d9ba7a8e94201d00ad8154/manifests/sources.toml) for this reason. Shared non-forked address/protocol/encoding/transparent crates remain legitimate dependencies. An optional upstream comparison backend should be built separately and compared through serialized protocol data, not mixed through Rust type aliases.

### Network interfaces that must be validated individually

The canonical [`CompactTxStreamer` schema](https://github.com/zcash/lightwallet-protocol/blob/12b892541bbf14d8e485a13e63ccfac85382fc21/walletrpc/service.proto) defines latest/block-range access, raw transactions, submission, transparent transactions/balances/UTXOs, tree states/subtree roots, mempool streams and server information. `GetBlockRange` is server-streaming; `SendTransaction` returns an error code/message. The [compact schema](https://github.com/zcash/lightwallet-protocol/blob/12b892541bbf14d8e485a13e63ccfac85382fc21/walletrpc/compact_formats.proto) represents scanning data, not full transaction bodies or arbitrary JSON-RPC blocks.

Node JSON-RPC examples include [`getblock`](https://zcash.github.io/rpc/getblock.html), [`z_gettreestate`](https://zcash.github.io/rpc/z_gettreestate.html), and [`sendrawtransaction`](https://zcash.github.io/rpc/sendrawtransaction.html). The retrieved official pages identify themselves as **Zcash 6.12.2**; they are reference semantics, not proof of current Zakura/Zebra/Zaino parity. Direct Zakura RPC source retrieval at guessed paths failed, so no exhaustive Zakura method inventory is claimed.

Zaino is a Rust indexer with gRPC/JSON-RPC serving components; its [README](https://github.com/zingolabs/zaino/blob/dev/README.md) mixes present architecture and future goals. Validate actual methods and schemas per deployed release. [Zebra's lightwalletd guide](https://github.com/ZcashFoundation/zebra/blob/main/book/src/user/lightwalletd.md) documents the validator/indexer split. Avoid treating lightwalletd, Zaino, a node RPC and a wallet daemon RPC as interchangeable providers.

Proposed transport contracts need endpoint/network identity, supported methods/pools, protobuf revision, authentication, cancellation, backpressure, retries, deadlines, TLS/CORS and trust metadata. Never imply broadcast success is mining confirmation. Reconnect/resume, missing history after pruning, malformed responses, stale tips and reorgs must be represented. A browser gateway is a separate deployment requirement: ordinary browser fetch is not a native tonic HTTP/2 channel, and [gRPC-Web](https://github.com/grpc/grpc-web/blob/master/README.md) has proxy and streaming-mode constraints.

## PRELIMINARY architecture and API-surface taxonomy

These are candidate boundaries and naming sketches, **not existing zcash.js functions or a final package plan**. Recommend one stable TypeScript API for the fully fledged Node.js product, with runtime-selected internal backends. Package labels below describe candidate logical boundaries; they do not prescribe separately installed products or backend-specific public APIs.

Proposed flow:

`application → public/query client or wallet client → host engine → coherent Rust crypto/wallet stack`

Transport and durable storage are supplied through explicit adapters. A proving worker is a separate computational capability; a signer is a separate authority. Basic public queries should not initialize secret storage or download proving assets.

| PRELIMINARY candidate module / package | PRELIMINARY JS surface families | Lower-level Rust/WASM responsibilities |
| --- | --- | --- |
| `zcash` / `@zcash/core` | Chain definitions, amounts (bigint zatoshis), byte/hex types, address/URI codecs, memo handling, errors, capability descriptors. | Consensus-sensitive parsing/encoding and validation; avoid duplicate divergent crypto implementations. |
| `@zcash/client` | `createPublicClient`; block/header/tip/transaction/UTXO/tree queries, bounded range iteration, mempool and confirmation/reorg observation, submission of finalized bytes. | Optional parsing/validation only; network orchestration in host adapters. No fabricated Ethereum gas/log/contract model. |
| `@zcash/transports` | JSON-RPC, lightwallet protocol, browser gateway and mock/offline transports; method capability negotiation. | Usually none; Rust protobuf decoding may be useful if it avoids extra copies. Transport choice remains outside cryptographic primitives. |
| `@zcash/keys` | Seed/account derivation, spending/viewing capabilities, address/diversifier selection and import/export; explicit secret lifetime. | Transparent, Sapling and Ironwood key/address coverage must be validated in Common/wallet. Opaque secret handles; network and scope checks. |
| `@zcash/transactions` | Decode/encode/inspect; fee estimation; proposal/build stages; transparent/Sapling/Ironwood and supported mixed-pool payments; PCZT role workflows and finalization. | Protocol builder, sighash/authorization, bundle validation and PCZT operations. Host representations must preserve exact amounts and authorization state. |
| `@zcash/proving` | Prover discovery, preparation, proof jobs/progress/cancel/dispose, parameter-provider integration. | Validate exact Ironwood circuit/proving contexts and branch compatibility; Orchard evidence alone is insufficient. Sapling/Groth16 parameters, proving authority and target-runtime behavior require v1 validation. No built-in network access or unapproved remote witness transfer. |
| `@zcash/scanning` | Viewing-only scanning sessions; compact/full transaction ingestion; note/nullifier results; scan progress, rewind and checkpoint handling. | Trial decryption, trees/witnesses and wallet data-API operations, with atomic storage contracts. |
| `@zcash/wallet` | `createWalletClient`; create/restore/import accounts, sync, balance/history/notes, receive, send/shield, locks/reservations, backup/recovery and watch-only workflows. | Wallet state machine, proposal/selection and spendability rules. Keys, signer, prover, storage and transport supplied as capabilities. |
| `@zcash/signers` | Local opaque signer, first-class offline/PCZT and generic hardware/custom signer adapter seams (concrete Ledger is an unsupported documented placeholder); requests tied to a reviewed transaction. | Signing/authorization only where supported; external adapters declare pools/versions/roles. FROST feature presence does not deliver a complete multisig wallet UX; multisig and remote-wallet RPC are out of current scope and must not be designed now (D25). |
| `@zcash/storage-*`, `@zcash/wasm`, optional native host | Node/browser storage adapters, worker/runtime initialization, ABI version/capability reporting, disposal and diagnostics. | Storage bridge, host services, bounded handles/buffers/jobs. Native Node acceleration is deferred benchmark-triggered work, with no parity or shipment promise. |

The [transaction/query plan](../planning/transaction-query-api.md) supersedes lifecycle sketches: expose PCZT manual stages and fused local send composition. A viem/ethers-inspired preliminary `send` returns a typed pending handle with preliminary `wait` semantics; preliminary `propose`, `build`, `prove`, `sign`, `finalize`, `broadcast` and `watch` remain available. All names are sketches. Ordering depends on protocol/PCZT roles; composition must preserve reviewed-plan identity, reveal privacy disclosures before affected actions and expose unknown broadcast outcomes. Define confirmations, reorgs, expiry, cancellation and partial multi-transaction results without treating submission as settlement.

The API must distinguish public chain data, locally scanned wallet data and remotely managed wallet state. In particular, a unified address does not expose a queryable private account balance; an incoming viewing key cannot be advertised as complete spending-history authority. [Unified viewing-key semantics](https://zips.z.cash/zip-0316), [key types](https://github.com/zakura-core/common/blob/2e501116b60741136db21f4584f0d6d8378444a6/crates/zcash_keys/src/keys.rs).

Candidate host ABI taxonomy: runtime/capabilities; codecs; key handles; transaction/PCZT contexts; scan sessions and state deltas; proof contexts and assets; signer operations; job lifecycle; typed errors; buffer/handle disposal. Host imports should be limited to explicitly selected entropy, storage, scheduling/progress and asset services. Avoid exporting all Rust internals or synchronous per-note callbacks that would entangle async IndexedDB with Rust borrowing. This is an inference from the observed layer split, pending prototypes and full API review.

## Decisions and validation required before full API design

Use the [decision log](../planning/decision-log.md) for classifications and rationale; do not reopen settled owner scope merely because the source inventory is broader.

1. **Backend/version validation:** select a coherent Common/wallet graph and wrapper design; preserve the minimal upstreamable target-fix policy (D01). Validate Sapling and Ironwood separately, without extrapolating Ironwood coverage from Orchard (D04–D06).
2. **Node delivery:** functionally qualify the WASM-first worker/VFS path under D07; defer performance budgets and possible native/N-API comparison to the future benchmark issue (D02–D03a).
3. **Storage:** validate the D07 Rust-owned SQLite/OPFS path, transactions, Sapling/Ironwood witnesses, checkpoints, reorg recovery, reservations and backup/migration. Preserve D16a memory/application/external secret custody and D17 Zakura-owned account indexing.
4. **Transport:** select host adapters, endpoint/schema capabilities, privacy/trust policies, streaming and ambiguous-broadcast behavior through D08. Indexer and node roles remain distinct; remote-wallet RPC is out of current scope and must not be designed now (D25).
5. **Transaction lifecycle:** specify manual and composed paths, typed pending/wait behavior, privacy review, protocol/PCZT ordering and multi-transaction recovery; keep every public name preliminary (D09).
6. **Prior art:** derive requirements from WebZjs without API/snapshot compatibility or completeness assumptions (D10).
7. **Signer/prover boundaries:** validate device/firmware/pool/role support for first-class external signer/PCZT seams (D11). Keep remote proving deferred while preserving a future prover extension seam (D12–D13).
8. **Remaining API details:** review factories/actions, exports, errors, serialization, events/iterators, authority, cancellation and extension interfaces. Sprout remains deferred until an explicit scope reconsideration (D05).

The next step is the [full JS and Rust/WASM API validation workplan](../planning/api-surface-workplan.md), not implementation from this taxonomy.
